# Support Copilot — ассистент поддержки и разбора жалоб

Решение кейса 03 (Grand Mobile, Decentrathon 6.0). Сервис принимает обращение игрока и возвращает структурированный разбор: язык, категорию, приоритет, признак спама или дубля, извлечённые факты, черновик ответа с цитатами правил и решение, нужен ли человек.

Главный принцип: **не выдумывать правила и не обещать того, чего сервис не может.**

## Что делает программа

Для каждого обращения (`kind`: `complaint` или `report`, список сообщений):

1. **Нормализует текст.** Казахские буквы из cp1251 (`ќ ґ ѕ є ј ў ї`) заменяются на настоящие (`қ ғ ң ә ө ұ ү`).
2. **Определяет язык:** ru, kk, uz, en или und.
3. **Определяет категорию** (`complaint.insult`, `complaint.cheat`, `complaint.scam`, `report.payment`, `report.hack`, `report.appeal`, `report.bug`, `*.other`, `spam`) и **приоритет** p0–p3.
4. **Отсеивает спам** (ссылки, реклама, продажа аккаунтов) и **дубли**: один игрок, похожий текст или та же категория, окно один час.
5. **Извлекает факты:** ник обвиняемого, пункты правил из текста, наличие доказательств, сервер.
6. **Ищет пункты правил (RAG)** в `rules.json`. Если игрок не указал пункт, подбирается самый подходящий по словам.
7. **Пишет черновик ответа** на языке игрока (ru, kk, uz, en) со ссылками на пункты и текстом под категорию: что проверит администратор, что приложить, чего не сообщать.
8. **Решает, нужен ли человек**, и объясняет причину в `reasons`.

## Защита от галлюцинаций и пустых обещаний

- В `cited` попадают только пункты, которые реально есть в `rules.json`. Выдуманный игроком номер отбрасывается.
- Черновики собираются из шаблонов. В них нет обещаний наказания, разбана, возврата средств или решения по другому игроку.
- Всегда `needs_human: true` для: платежей, апелляций банов, взлома аккаунта, любых жалоб (наказание подтверждает администратор), просьб о разбане и возврате, неопределённого языка, низкой уверенности.
- Факты из жалобы не принимаются за истину: сервис только извлекает их, решение остаётся за администратором.

## Структура папки

| Файл | Назначение |
|---|---|
| `core.py` | Вся логика триажа. Только стандартная библиотека |
| `dedup.py` | Поиск дублей: один игрок, одна проблема, окно один час |
| `server.py` | Основной HTTP-сервис без зависимостей (стандартная библиотека): `POST /triage`, `GET /health` |
| `app.py` | Тот же сервис на FastAPI, необязательный вариант |
| `predict.py` | Пакетный прогон файла обращений и сводка (p95, доля «нужен человек», дубли) |
| `eval.py` | Accuracy по категории, macro-F1 по приоритету, проверка цитат, генерация `report.md` |
| `Makefile` | Команды `install`, `serve`, `predict`, `eval` |
| `rules.sample.json` | Маленький образец правил. Настоящий `rules.json` положите рядом, он подхватится автоматически |
| `category_map.example.json` | Привязка внутренних категорий к id из `taxonomy.json` |
| `sample_tickets.jsonl` | Пример входного файла из 7 размеченных обращений (придуманных мной) |
| `sample_report.md` | Пример отчёта на этих 7 обращениях. Это проверка работы скрипта, а не метрика качества |
| `requirements.txt` | `fastapi`, `uvicorn` (только для `app.py`) |
| `.gitignore` | Не даёт случайно опубликовать данные Grand Mobile |

## Запуск

```bash
make serve                        # python server.py: сервис на http://localhost:8000, ничего устанавливать не нужно
make serve-fastapi                # то же на FastAPI (сначала make install)
make predict IN=tickets.jsonl OUT=pred.jsonl
make eval OUT=pred.jsonl GOLD=tickets_valid_labeled.jsonl   # метрики и report.md
```

`predict.py` работает без FastAPI и понимает `.jsonl.gz`. Путь к правилам можно задать переменной `RULES_PATH`. Для `make eval` нужен файл, где у обращений заполнены `category` и `priority`.

Пример запроса:

```bash
curl -X POST localhost:8000/triage -H 'Content-Type: application/json' -d '{
  "kind": "complaint",
  "reporter_hash": "a91c",
  "created_at": "2026-03-14T19:02:00",
  "messages": [{"role": "player", "text": "Arman_Petrov оскорблял меня и мою семью в чате, скрины есть, 2.1 ОП", "attachments": 2}]
}'
```

`reporter_hash` и `created_at` необязательны, нужны только для поиска дублей. Ответ повторяет контракт кейса: `lang`, `category`, `priority`, `is_spam_or_duplicate`, `extracted`, `draft_reply {lang, text, cited}`, `needs_human`, `confidence`, `reasons`.

## Привязка к таксономии

Названия категорий в коде придуманы по смыслу кейса. Когда будет `taxonomy.json`: скопируйте `category_map.example.json` в `category_map.json` и впишите настоящие id. Больше ничего менять не нужно.

## Стоимость и латентность

Внешние LLM-API не используются: стоимость на обращение 0 $, обработка занимает около 1 мс. Требования кейса (до 0,002 $ и p95 до 5 с) выполняются с большим запасом.

## Ограничения текущей версии (честно)

- Категория, приоритет и спам определяются **эвристиками** (регулярные выражения). Метрики на настоящей валидации не считались: размеченных данных и скрытого теста здесь нет. Цифры в `sample_report.md` относятся к 7 примерам, которые я придумал сам, и о качестве ничего не говорят.
- Поиск по правилам лексический и проверен только на трёх образцовых пунктах. С полным `rules.json` качество нужно проверить.
- Тексты на kk и uz написаны вручную и коротки. Их нужно показать носителям.
- Базы знаний (инструкции, FAQ) нет: в данных кейса её нет, придумывать содержимое я не стал.
- Не сделаны: шаблоны ответов по кластерам обращений, интерфейс админа (бонус кейса). Дедупликация сделана в простом варианте (похожесть слов и категория).

## Куда развивать

1. Привести категории к `taxonomy.json`, посчитать accuracy и macro-F1 на `tickets_valid.jsonl`.
2. Заменить эвристики на модель: классификатор, обученный на 120 тыс. обращений, или LLM (тогда посчитать стоимость на тикет).
3. Векторный поиск по правилам вместо лексического.
4. Генерация черновиков LLM с проверкой, что каждая цитата существует в `rules.json`.
5. Подсказки из реальных ответов администраторов: поле `admin` в обучающих данных даёт готовые формулировки.
